## 🧾 요약

씨앤에이아이에서 Toss와 PayPal 결제 흐름의 안정성을 높이기 위한 백엔드 구조를 개발했습니다.

단건 결제와 정기구독 결제 흐름을 분리하고, 주문 단위 멱등키와 Redis Lock을 적용해 중복 승인과 내부 처리 실패 상황을 제어할 수 있도록 구성했습니다.

## 🔍 문제

결제 승인 요청은 네트워크 지연, 사용자 재시도, 클라이언트 중복 호출 등으로 같은 주문에 대해 여러 번 들어올 수 있었습니다. 이때 동일 주문이 중복 승인되면 실제 PG 결제 상태와 내부 주문 상태가 어긋날 수 있었습니다.

또한 PG 승인에는 성공했지만 내부 주문 처리나 구독 상태 반영에 실패하는 경우, 결제는 되었는데 서비스 상태는 갱신되지 않는 문제가 생길 수 있었습니다. 결제 흐름에서는 이런 중간 실패를 단순 오류로 끝내기보다, 이후 상태를 복구하거나 승인 취소로 되돌릴 수 있는 구조가 필요했습니다.

## 🛠️ 개선 과정

먼저 Toss 단건 결제와 PayPal 정기구독 결제의 처리 흐름을 분리했습니다. 결제 방식마다 승인 이후 처리해야 하는 내부 상태가 달랐기 때문에, 공통 결제 처리와 결제 수단별 후속 처리를 나눠 각 흐름의 책임을 명확히 했습니다.

동일 주문에 대한 중복 승인 요청은 주문 단위 멱등키와 Redis Lock으로 제어했습니다. 이미 처리 중인 주문에 대해서는 추가 승인 요청이 동시에 진행되지 않도록 막고, 처리 결과를 기준으로 이후 요청을 판단할 수 있게 했습니다.

PG 승인 이후 내부 주문 처리에 실패하는 경우에는 실패 보상 흐름을 구성했습니다. 내부 상태 반영이 완료되지 못하면 PG 취소 API를 호출해 결제 상태를 되돌리고, 결제 데이터와 서비스 데이터가 서로 다른 상태로 남지 않도록 했습니다.

## 📈 성과

동일 주문에 대한 중복 승인 가능성을 줄이고, PG 승인 이후 내부 처리 실패 상황을 보상 처리할 수 있는 기반을 만들었습니다.

결제 승인, 내부 주문 처리, 실패 보상 단계를 분리하면서 결제 흐름의 책임이 명확해졌고, 장애 상황에서도 추적하고 대응하기 쉬운 구조로 개선되었습니다.

## 🌱 회고

이전 직장에서는 활용하지 못했던 Redis를 결제 흐름에 적용해, 동일 주문에 대한 중복 처리 가능성을 제어해볼 수 있었다는 점에서 좋은 경험이었습니다. 또한 멱등키를 적극적으로 활용해 결제 요청이 반복되더라도 같은 주문이 중복 승인되지 않도록 결제 로직의 안정성을 높일 수 있었습니다.

다만 프로젝트가 중단되어 실제 운영 환경에서 적용 결과를 확인하지 못하고, 테스트를 통해서만 검증해야 했던 점은 아쉬움으로 남았습니다. 또한 결제 실패, 재시도 등 여러 케이스를 하나의 흐름 안에서 다루다 보니 내부 로직의 복잡도가 높아졌습니다.

다음 프로젝트에서 다시 결제 도메인을 맡게 된다면, 중복 처리와 실패 보상 흐름을 더 단순하고 명확하게 설계해 운영 환경에서도 안정적으로 검증해보고 싶습니다.
